# Context Window 为什么不是 Memory

## 1. 核心结论

Context Window 是模型一次推理能看到的 token 范围，但它不是长期记忆，也不是可靠数据库。

更准确地说：

```text
Context Window 是运行时资源。
Memory 是跨任务、跨会话保存和检索信息的系统能力。
```

`Lost in the Middle: How Language Models Use Long Contexts` 的核心发现是：

```text
模型更容易使用上下文开头和结尾的信息，
更容易忽略上下文中间的信息。
```

因此：

```text
能塞进上下文，不代表模型能稳定用到。
```

## 2. Context Window 是什么

Context Window 指模型在一次推理中能接收和处理的 token 范围。

例如一个模型支持 128K context，不代表它拥有 128K token 的长期记忆，只代表一次请求最多可以把约 128K token 放进输入。

从运行时角度看，Context Window 主要影响：

-   prompt 能放多少信息。
-   prefill 阶段需要处理多少 token。
-   KV cache 需要保存多少历史 key/value。
-   请求成本、延迟和显存压力。
-   Agent Runtime 如何做上下文选择、摘要、截断和检索。

## 3. Lost in the Middle 的实验结论

论文主要设计了两类任务。

第一类是多文档问答：

```text
给模型一个问题和多个文档。
其中只有一个文档包含答案，其余是干扰文档。
然后改变答案文档在上下文中的位置。
```

实验发现：

```text
答案文档放在开头或结尾时，模型更容易答对。
答案文档放在中间时，准确率明显下降。
```

第二类是 key-value 检索：

```text
给模型一组 key-value。
要求模型根据 key 找到对应 value。
```

这个任务更接近纯检索，排除了复杂自然语言理解和推理干扰。结果仍然显示：部分模型在中间位置检索信息时更不稳定。

这说明：

```text
长上下文模型的问题不只是“问答任务太复杂”，
而是模型对长上下文中间位置的信息使用本身就可能不稳定。
```

## 4. 为什么开头和结尾更容易被关注

原因不是模型显式认为中间不重要，而是首尾位置更容易被模型稳定利用，中间位置更容易在长上下文的信息竞争中被淹没。

### 4.1 生成任务天然偏向最近上下文

对 decoder-only 模型来说，预测下一个 token 时，最终主要使用最后一个位置的 hidden state。

这个位置离上下文末尾最近，所以末尾信息有更直接的路径影响输出。

这就是 recency bias：

```text
越靠近生成位置的信息，越容易被模型使用。
```

### 4.2 开头通常承载任务框架

上下文开头经常放：

-   system instruction
-   任务说明
-   背景设定
-   格式要求
-   问题或目标

模型在训练和使用中经常学到：

```text
开头内容定义任务，结尾内容定义当前要回答什么。
```

所以首部内容也更容易被保留为全局任务条件。

### 4.3 中间信息缺少位置锚点

中间位置既不靠近任务开头，也不靠近当前输出位置。

它不像开头那样定义任务，也不像结尾那样贴近回答位置。因此在大量相似文本片段中，中间信息更容易变成普通片段。

在 RAG 场景中尤其明显：

```text
文档 1
文档 2
文档 3  <- 相关信息
文档 4
文档 5
问题
```

如果每个文档结构类似，相关文档会和干扰文档竞争注意力，模型不一定能稳定把它挑出来。

### 4.4 Attention 不是完美检索机制

一个常见误解是：

```text
有 attention = 模型可以精准访问任意 token
```

这不成立。

Attention 是加权信息混合，不是数据库索引。上下文越长，候选 token 越多，相关信号越容易被稀释。

如果中间信息没有强触发词、结构标记或与问题的直接匹配，它就可能被弱化。

### 4.5 训练分布会带来位置偏好

很多训练文本天然有结构：

```text
标题 / 摘要 / 开头交代主题
正文展开细节
结尾总结或回答
```

模型可能从数据中学到一种统计偏好：开头和结尾的信息更常用于判断任务或生成答案。

这不是显式规则，而是训练分布带来的行为倾向。

## 5. 为什么长上下文不等于长期记忆

长上下文只解决了一个问题：

```text
一次请求里可以放更多 token。
```

它没有自动解决这些问题：

-   哪些信息应该进入上下文。
-   进入上下文的信息如何排序。
-   中间信息是否能被稳定使用。
-   历史信息是否应该被压缩。
-   跨会话事实如何更新。
-   旧信息和新信息冲突时如何处理。
-   哪些内容是用户偏好、项目事实、任务状态或临时上下文。

这些问题需要 Memory、Retrieval、State 和 Context Manager 来解决。

所以：

```text
Context Window 是容量。
Memory 是选择、保存、检索、更新和治理机制。
```

## 6. 对 RAG 和 Agent Runtime 的启发

对 RAG 来说，不应该简单认为：

```text
检索越多越好。
```

论文显示，增加文档数量可能提高 retriever recall，但 reader 模型不一定能更好回答。超过一定数量后，多给文档会增加成本和延迟，却不一定提升准确率。

更稳的做法是：

-   控制放入上下文的文档数量。
-   把最相关内容放在靠近问题或回答位置的地方。
-   对文档做排序、去重和截断。
-   给关键片段加清晰标题、编号和来源。
-   对长内容做摘要和分层组织。
-   不把所有历史无差别塞进 prompt。

对 Agent Runtime 来说，需要专门的 Context Manager：

```text
Memory Store
    -> Retrieval
    -> Ranking
    -> Compression
    -> Context Assembly
    -> Model Call
```

Runtime 需要判断：

-   当前任务必须放进上下文的内容是什么。
-   可以检索但不必全部放入的内容是什么。
-   应该摘要的内容是什么。
-   应该写入长期记忆的内容是什么。
-   应该保留为任务状态的内容是什么。

## 7. 一句话总结

```text
Context Window 决定模型一次能看多少 token，
但不保证模型能同等稳定地使用每个 token。
```

Agent Runtime 不能依赖“把所有东西塞进 prompt”。更可靠的方向是：

```text
检索相关信息，
压缩历史内容，
把关键内容放在更容易被模型使用的位置，
并用 Memory 和 State 管理跨任务信息。
```
